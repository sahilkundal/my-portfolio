ELAN — building a design system for a service ecosystem

The original ELAN v1.0 file is dated July 2021; the story below describes how the system evolved through my Onsitego tenure and how its reusable principles supported multiple product surfaces.

01

The challenge wasn't inconsistency. It was repetition.

Onsitego's product ecosystem was expanding across customer experiences, retailer tools, field-service applications and internal operations. Different products were solving the same interface problems independently: buttons, forms, cards, statuses, navigation, tables, service states and product/service imagery.

That created a familiar scaling problem. A designer could make a polished screen, but the next product would reinterpret the same pattern. Developers then implemented slightly different versions. Over time, small differences became a system-level problem: more design debt, more QA exceptions and more cognitive load for users moving between products.

“The goal was not to make every screen look identical. The goal was to make every familiar interaction behave predictably.”
02

Start with an ecosystem audit

I treated the existing products as the raw material for the system rather than starting from a blank component library. I reviewed recurring UI patterns, grouped visual duplicates, compared interaction states and identified where a single reusable rule could replace several one-off decisions.

01

Inventory

Collect recurring controls, layouts, icons, imagery and content patterns from existing products.

02

Consolidate

Separate true product-specific behaviour from patterns that should become shared primitives.

03

Prioritise

Build the highest-reuse components first, then extend the system as new workflows exposed new needs.

Design principle: I used real product problems to decide what belonged in ELAN. This kept the system grounded in actual workflows instead of becoming a collection of visually attractive but rarely-used components.
03

Build the foundation before the library

The system was organised from the smallest visual decisions to the patterns users encountered repeatedly. The intent was to make a designer's decision path shorter: choose the foundation, compose the component, then assemble the product pattern.

FOUNDATIONS

Visual language

Color, typography, spacing, radius, hierarchy, iconography and imagery rules created a common visual grammar.

COMPONENTS

Reusable building blocks

Buttons, inputs, selectors, cards, navigation, tabs, status treatments, tables and common controls were consolidated into reusable Figma patterns.

PATTERNS

Product-level behaviour

Service requests, customer information, dashboards, forms, operational states and field workflows translated primitives into useful product structures.

04

Design for states, not just the happy path

One of the most important shifts was treating a component as a behavioural object rather than a screenshot. A button isn't just its default appearance; an input isn't complete without validation; a service status isn't useful without a consistent semantic model.

Component thinking

One component → many product moments

Visual states

  • Default
  • Hover / pressed
  • Focus
  • Disabled
  • Error / success where relevant

UX behaviour

  • When to use it
  • What happens after interaction
  • Content constraints
  • Responsive behaviour
  • What not to do

This reduced the tendency to recreate a component every time a new screen required a slightly different state. The system became a decision framework as much as a visual library.

05

The asset library mattered too

ELAN wasn't only a UI-component library. The Figma file also contained a broad visual asset ecosystem: appliance imagery, electronics, service imagery, brand references, promotional graphics, payment marks and utility illustrations.

That mattered because Onsitego's interface often had to communicate a physical product or a service context. Reusing an approved visual vocabulary made those experiences feel related even when the workflows were very different.

06

Make the system useful across very different products

The real test of ELAN was not how complete the Figma page looked. It was whether the same system could support different jobs without forcing them into the same UI.

FIELD SERVICE

Livtrack

Fast, task-oriented workflows for service engineers. The system provided consistent controls and states while allowing the interaction density to remain appropriate for on-the-go work.

Outcome across the ecosystem: service completion loops were reduced by 15% during the later optimization work.
OPERATIONS

Enterprise dashboards

Dense information environments needed stronger hierarchy, predictable tables, filters, statuses and scanning patterns without losing the underlying product language.

Outcome: daily stakeholder dashboard usage increased by 30% after the broader dashboard improvements.
RETAIL / PARTNER

SalesPro & partner workflows

Retailer-facing workflows could reuse the same interaction vocabulary while adapting content and task priorities to partner needs.

Outcome: retailer platform interactions increased by 25% in the broader redesign work.
CUSTOMER EXPERIENCE

Website & service journeys

Customer-facing experiences used the same principles for hierarchy, forms, cards and service communication, reducing the visual distance between touchpoints.

Outcome: customer inquiries decreased by 10% after service-request and onboarding improvements.
07

From Figma library to team workflow

A design system only creates leverage when people actually use it. I maintained the centralized Figma library, reused it in product work and evolved it as new requirements appeared. That created a feedback loop between system work and product work:

A product exposes a repeated problem.
The pattern is compared with existing ELAN components.
If the need is broadly reusable, the component/pattern is standardised.
The updated system is reused in subsequent product work.
Product work becomes the test environment for the design system.

By maintaining the system inside the same tool used for day-to-day design, the distance between “the design system” and “the product” stayed small. It was a living library, not a separate documentation project that designers had to remember to consult.

The strongest evidence of impact came from the products that the system supported rather than from a vanity component count. Across the broader product work, the ecosystem saw:

  • −15% field-service completion loops in Livtrack optimization.
  • +30% daily stakeholder usage on enterprise dashboards.
  • −10% customer inquiries after service-request and onboarding improvements.
  • +25% retailer platform interactions in the partner/CRM redesign work.
  • +20% net user satisfaction in the later Livtrack optimization work.

These are product-level outcomes from work conducted using the centralized design-system approach; they should not be interpreted as isolated causal effects of ELAN alone.

09

What I would improve in a modern ELAN 2.0

The original system was built around the needs and tooling of its time. If I were evolving it today, I would make the architecture even more explicit and developer-connected.

01

Token-first architecture

Formal semantic tokens for color, spacing, typography, elevation and component states, with clear primitive → semantic relationships.

02

Stronger documentation

Component anatomy, usage guidance, accessibility requirements, content rules, responsive behaviour and do/don't examples beside every major component.

03

Design-to-code parity

Closer mapping between Figma variables/components and front-end primitives so the system becomes a shared contract between design and engineering.

10

What this project changed about how I design

ELAN changed my definition of a “good screen.” I stopped evaluating design only at the page level and started looking for the rules underneath the page: what repeats, what varies, what needs a state, what should be shared, and where consistency would genuinely reduce user effort.

That systems mindset now carries into my work on enterprise AI products. The same question applies whether I'm designing a button, a service workflow or an AI recommendation: what rule makes the next experience easier to design, build, understand and trust?
